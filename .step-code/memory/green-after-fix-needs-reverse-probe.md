# 测试转绿不等于修复起效，必须反向探针

2026-08-11 修 AIASys canvas e2e 时连续两次归因错误，都是同一个形态。

## 现场

失败用例 canvas-preview-ctrl-wheel:63（subpath 没落盘）。我判断是产品缺陷「debounce
未完成就卸载，pending 丢失」，在 useCanvasHandlers 加了卸载时 flush，同时顺手给测试加
了一条中间 poll。重跑转绿，我准备记成「修复成功」。

反向探针（把 flush 摘掉、其余不动）**仍然通过** → 转绿与修复无关，真正起作用的是那条
中间 poll 带来的等待窗口，原失败是测试缺等待。

第二次同样：新写的 canvas-unsaved-flush 用 `clock.runFor(2000)` 推进时间后绿，摘掉 flush
依然绿——runFor 会把还活着的 debounce 定时器一并唤醒，断言变成必然成立。

## 动作

修复后测试转绿时，绿本身不构成证据。必须做一次反向探针：**只回退修复、保留测试改动**，
重跑确认变红。变红才说明修复与转绿有因果。

同一轮里既改产品又改测试，是归因失败的高发场景——转绿有两个候选原因，默认归给自己改的
产品代码就是幻觉。要么分两次跑，要么用反向探针切开。

针对时间/异步的测试，还要多问一句：我加的等待或时钟推进，是否把待测场景本身绕过去了？
「等到落盘完成再继续」会让「未落盘就切走」这个前提不再成立。
